建议把它设计成一个 **“以考试得分为目标的个性化刷题与补弱系统”**，而不只是“上传试卷，让 LLM 总结、讲题”。

它应当持续回答三个问题：

**我接下来学什么最值得？这道题我为什么不会？怎样证明我已经掌握，而不只是看懂了解析？**

你的 Python 背景适合先做成一个**模块化单体 Web 应用**：题库、学习记录和调度规则由后端确定性管理，LLM 负责识别、理解、讲解和生成候选内容。首版按“个人自用、一个考试先跑通”设计，同时保留多用户与多考试扩展能力。

下面所有学习阈值和时间分配都是**可配置的产品设计起点**，不是已经验证的提分承诺。

# 一、产品的核心闭环

整个系统围绕下面这个闭环运行：

```text
导入近五年真题、答案、考试大纲
                ↓
识别并拆分题目，校验答案与来源
                ↓
建立“题目—考点—题型—解题方法”关联
                ↓
统计历年分值分布，进行个人能力诊断
                ↓
生成今日学习任务
                ↓
作答 → 判分 → 识别薄弱环节
                ↓
针对性讲解 → 小练习 → 陌生变式验证
                ↓
更新学习状态，安排后续复习
                ↓
未见过的限时测验，检验实际提分
```

**重点是让学习过程产生可验证的作答证据，而不是不断生成更多总结。**

练习测试和分散到不同时间的学习，是学习技术研究中获得较高效用评价的方法。因此，这个产品应该把“主动作答”和“间隔复习”放在核心位置，而不是让用户主要阅读 AI 笔记。:chatgpt-content-reference{index="0"}

## 首次进入应用

创建一个“考试项目”，至少设置：

| 配置 | 用途 |
|---|---|
| 考试名称、科目、考试日期 | 确定内容范围与剩余时间 |
| 目标分数、总分、及格要求 | 区分保通过与冲高分策略 |
| 每日可用时间 | 限制任务量，避免计划无法完成 |
| 大纲版本、教材版本 | 防止旧知识与当前要求混用 |
| 题型及计分规则 | 支持多选部分得分、倒扣分、主观题评分等差异 |
| 真题年份、场次和完整性 | 确定五年分析的数据覆盖范围 |

不要把“近五年”硬编码成某五个年份，而应根据用户导入的**最近五个完整考试年度或考试周期**确定。

# 二、Web 界面怎么设计

建议首版保留六个主要页面，不要一开始做成庞大的教学平台。

| 页面 | 核心功能 | 需要突出展示的信息 |
|---|---|---|
| **今日学习** | 开始今日任务、继续未完成任务 | 今天学什么、为什么学、预计占用多少时间 |
| **题库与导入** | 图片上传、文字粘贴、批量导入、校对 | 原图、识别结果、答案来源、待处理问题 |
| **考点地图** | 查看考点关系和历年分布 | 分值权重、个人薄弱点、尚未覆盖的内容 |
| **刷题工作台** | 答题、提示、讲解、变式训练 | 当前题目、作答区、按需展开的辅导区 |
| **错题与复习** | 按原因和考点复习 | 哪种错误反复出现，而不只是错题列表 |
| **模拟考试与报告** | 限时考试、交卷分析 | 陌生题得分、用时、失分结构 |

## 刷题工作台是最重要的页面

桌面端可以采用：

```text
┌─────────────────────────────────────────────────────┐
│ 当前任务：排列与组合 · 第 3/8 题 · 练习模式           │
├───────────────────────────────┬─────────────────────┤
│                               │                     │
│ 题干、图片、表格、公式         │ AI 辅导区           │
│                               │                     │
│ 选项 / 输入框 / 手写照片上传   │ 默认不直接展示答案  │
│                               │                     │
│                               │ [给一点提示]        │
│                               │ [解释这个条件]      │
│                               │ [完整讲解]          │
│                               │ [我哪里理解错了]    │
├───────────────────────────────┴─────────────────────┤
│ [提交答案]                 把握程度：确定 / 不确定    │
└─────────────────────────────────────────────────────┘
```

手机端改为上下布局，并优先支持拍照、裁剪和继续作答。

**练习模式与考试模式必须分开。**练习模式允许提示和讲解；考试模式不提供这些入口，答案也不能提前下发到浏览器。

# 三、图片和文字如何变成可靠题库

这部分是整个系统的质量基础。题目识别错一个“不”、负号或者单位，后面的判分、讲解和学习状态都会受影响。

## 3.1 导入流程

```text
上传图片 / 粘贴文字
        ↓
保存原始材料与来源信息
        ↓
文字直接解析；图片进行视觉识别与版面分析
        ↓
识别题号、题干、选项、图表、公式、子问题
        ↓
拆分为结构化题目
        ↓
匹配答案与解析
        ↓
检测缺项、冲突、重复及识别疑点
        ↓
必要的人工作业校对
        ↓
发布到可练习题库
```

实现时建议分两条路径：

**单题截图、拍照：**优先使用多模态模型理解整张题图，同时保留原图。图片中的几何关系、标注位置、表格结构不能只靠一段识别文字代替。

**批量扫描试卷：**使用版面分析工具处理题块、阅读顺序、表格和公式，再把复杂区域交给视觉模型。PaddleOCR 的 PP-StructureV3 提供版面分析、表格与公式识别、多栏阅读顺序恢复等能力，可以作为这一层的候选组件。:chatgpt-content-reference{index="1"}

有原生文字时直接使用文字，不要重复走图像识别。

## 3.2 不能把整页文字简单切块

题目不是普通 RAG 文档段落，需要保留结构：

```text
材料题
  ├── 公共材料
  ├── 公共图表
  ├── 子题 1
  ├── 子题 2
  └── 子题 3
```

必须处理跨页题、共享材料、独立答案页，以及题目中引用的附图。

每道题都应能追溯到：

```text
原始文件 → 页码 → 图像区域 → 题号 → 当前题目版本
```

对用户上传的手写解题过程也一样：先展示识别结果供确认，再据此诊断；不清楚的步骤不要替用户补写。

## 3.3 答案来源与验证状态要分开

建议设计两个独立维度：

```text
答案来源：
官方答案 / 教材或题库答案 / 用户提供 / AI 推导

验证状态：
待校验 / 已核对 / 有争议
```

“来自官方答案”说明来源，不代表系统已经正确匹配了题号；“AI 多次得到相同答案”也不等于已经验证。

没有可靠答案的题，可以进入“探讨模式”，但**不能直接作为确定的判分依据，也不能用于更新掌握状态**。

识别不清、答案缺失、来源冲突的题，应进入待处理队列，而不是让模型猜一个答案后悄悄发布。

# 四、如何分析近五年的考点和重点

这里需要同时完成两件事：

**LLM 理解每道题考什么；数据库准确统计这些考点出现了多少、占了多少分。**

不要让 LLM 看一批题后直接编写“某考点五年出现了 18 次”这种统计结果。

## 4.1 建立四层知识结构

建议使用：

```text
科目
 └── 章节 / 知识领域
      └── 考点
           └── 具体考查方式 / 题型模板
```

例如：

```text
数学
 └── 计数问题
      └── 排列与组合
           ├── 判断是否需要考虑顺序
           ├── 带限制条件的选择
           └── 分类计数与重复计数
```

再单独维护“前置知识关系”：

```text
理解“顺序是否重要”
        ↓
区分排列与组合
        ↓
处理带限制条件的计数题
```

这样，用户不会一道复杂题时，系统能够定位到具体缺失的前置知识，而不是让他重学整章。

**初期用关系表保存这些关系即可，不必额外引入图数据库。**

## 4.2 每道题需要的分析标签

建议至少包括：

| 标签 | 作用 |
|---|---|
| 主考点、辅助考点 | 确定主要训练目标 |
| 题型与解题方法 | 推荐同类题、辨别方法混用 |
| 前置知识 | 决定需要补哪一小块知识 |
| 关键条件 | 指出题目中决定解法的条件 |
| 常见错误候选 | 为后续诊断提供线索，但不直接认定用户犯了该错误 |
| 来源年份、场次、分值 | 支持历史分析 |
| 大纲适用状态 | 区分当前适用、需要重审、已不适用 |

考点词表最好从考试大纲开始建立。没有大纲时，模型可以先提出候选分类，但需要审核、合并同义词，避免同一考点出现多个名字。

## 4.3 五年分析应该输出什么

建议输出以下结果，而不是单一“高频考点排行榜”：

| 分析结果 | 回答的问题 |
|---|---|
| 各考点年度分值占比 | 哪些内容长期占分较多？ |
| 各考点出现年度数 | 哪些内容持续出现？ |
| 考查方式变化 | 同一知识点近年换了什么问法？ |
| 大纲覆盖缺口 | 有哪些要求尚未被导入题库覆盖？ |
| 个人失分与考点交叉分析 | 哪些重要内容恰好是我的薄弱项？ |

统计必须处理三个细节。

**第一，区分重复导入和真实重复出题。**同一张试卷上传两次，不能统计两次；同一道题在不同年度真实出现，应保留两次考试记录。可以复用题目内容，但不能合并掉考试发生记录。

**第二，多考点题不能重复计算分值。**一道 10 分题关联三个考点，不能给每个考点都计 10 分。可以根据评分点拆分，或使用总和为 1 的分值归属权重。材料题的父题和子题也不能重复计分。

**第三，缺失年份不能当成零出现。**如果实际只有四年完整试卷，应明确展示覆盖范围。历史频率也不能直接写成“明年出题概率”。

# 五、做错题之后，LLM 应该怎么教

这是产品最有价值的部分：**不是给用户一篇更长的解析，而是找到当前阻碍解题的最小问题。**

## 5.1 先区分不同情况

建议记录：

```text
不会相关知识
知道知识，但不知道何时使用
选择了错误的方法
忽略或误解题目条件
计算、单位或符号出错
表达不符合评分要求
时间不足
猜中答案
题目或答案本身有问题
暂时无法判断原因
```

这些只能先作为诊断候选。

**只凭选错一个选项，通常不足以确定具体错误原因。**系统应根据用户的解题过程判断；证据不足时，用一个简短问题进一步区分。

不要默认把无法解释的错误归为“粗心”。

## 5.2 一次完整辅导的流程

```text
保存原始作答
      ↓
按题型判分
      ↓
读取用户步骤、提示使用情况与相关学习记录
      ↓
提出错误原因候选
      ↓
必要时问一个诊断问题
      ↓
解释当前缺失的知识
      ↓
给一个小练习
      ↓
给一道没有见过的变式题
      ↓
根据作答证据更新状态
```

用户可以直接要求完整讲解，不必强迫每个人都经历漫长的问答。但系统应记录答案是否已经展示，避免把之后的重答算作独立掌握。

## 5.3 一个具体例子

假设题目是：

> 从 5 人中选出 2 人参加活动，不区分职位，有多少种选法？

用户回答 `20`。

系统不要只回复：

> 应该用组合，答案是 10。

更合适的辅导是：

**先确认理解：**

> 你在计算时，是否把“选到甲和乙”与“选到乙和甲”算成了两种？

如果用户确认，讲解就聚焦于这一点：

> 这里两种情况选中的是同一组人。你计算的 \(5\times4\) 把每组人按先后顺序数了两遍，所以应再除以 2，得到 10。

随后给一道对比题：

> 如果改成选一名队长、一名副队长，答案还需要除以 2 吗？

再给一道独立变式：

> 从 6 人中选 2 人，不区分职位，有多少种选法？

这套练习要验证的是：

**用户是否理解“顺序是否影响结果”，而不是是否记住了原题答案。**

## 5.4 讲解结构要固定

每次讲解默认围绕：

```text
这道题在考什么
→ 关键条件是什么
→ 当前错误或卡点在哪里
→ 正确方法为什么适用
→ 哪些相似情况下不能这样做
→ 接下来做什么来验证
```

详细推导可以展开，默认先给能解决当前问题的内容。

# 六、如何判断“掌握了”，并安排下一题

这里建议拆成两个独立模块。

## 6.1 知识记忆状态

负责定义、公式、适用条件、易混概念等内容。

可以把它们转成小型主动回忆卡：

```text
正面：什么情况下，选两个人需要区分先后顺序？
背面：当两个位置或角色不同，交换人选会产生不同结果时……
```

调度层可以使用 `py-fsrs`。它支持根据卡片复习记录安排后续时间，并保存调度状态与复习日志。:chatgpt-content-reference{index="2"}

但在本系统中，FSRS 只负责这类记忆任务的复习调度，**不把“能回忆公式”直接视为“能完成陌生综合题”**。

## 6.2 解题能力状态

建议先不用一个看起来精确的“掌握率 87.3%”，而是展示证据驱动的状态：

```text
未诊断
  ↓
需要补基础
  ↓
提示后能完成
  ↓
可以独立完成
  ↓
可以处理陌生变式
  ↓
经过延迟验证
```

每个考点维护：

```text
独立作答次数
独立正确次数
接触过的题型模板
陌生变式表现
隔天或更久后的表现
用时与限时要求
提示和答案暴露记录
近期反复出现的错误
```

一个可配置的初版晋级规则可以是：

> 至少完成三次无提示正确作答，覆盖两种不同变式，其中包含一次延迟测验，并满足相应限时要求。

这只是产品规则，不应被展示为经过校准的知识掌握概率。不同科目、题型需要不同规则。

## 6.3 下一步学什么

首版使用透明、可解释的排序规则即可：

\[
优先级(k)
=
\frac{
考试权重(k)
\times 当前薄弱程度(k)
\times 短期可改善程度(k)
}{
预计学习时间(k)
}
+
到期复习加分(k)
\]

这里的考试权重来自当前大纲与已导入真题；薄弱程度来自作答证据。短期可改善程度在冷启动时只能使用规则估计，后续再根据学习记录校准。

**这是任务排序分数，不是预计能提高多少考试分数。**

同时加入约束，避免系统永远推荐最容易得分的少数考点：

```text
保留一定时间覆盖尚未诊断的大纲内容
限制一天内同题和同模板的重复次数
优先处理即将遗忘的已学重点
缺前置知识时，先补前置知识
总任务量不得超过用户时间预算
```

例如，用户每天只有 60 分钟时，可以先用“15 分钟复习、25 分钟补弱、10 分钟陌生题、10 分钟限时练习”作为初始配置，再根据表现调整。

# 七、推荐的技术架构

## 7.1 首版选型

结合你的 Python 背景，我建议：

| 层次 | 建议技术 | 在本项目中的职责 |
|---|---|---|
| 前端 | React + TypeScript + Vite | 刷题、导入校对、学习报告 |
| 数学展示 | KaTeX，复杂场景保留原图 | 题目与解析的公式展示 |
| 后端 | **Django + Django Ninja** | 用户、题库、考试、学习记录与 API |
| 内容后台 | Django Admin + 自定义校对页面 | 题目、答案、标签审核 |
| 数据库 | **PostgreSQL + pgvector** | 业务数据、来源信息、向量检索 |
| 异步任务 | Celery + Redis | 批量解析、标签生成、索引更新 |
| 文件存储 | 首版本地受控目录，封装 S3 兼容接口 | 原图、裁剪区域、用户作答图片 |
| AI 接入 | 自建模型适配层 | 视觉、文本推理、嵌入服务 |
| 部署 | Docker Compose | 先单机运行，独立扩展耗时任务 |

这里选择 Django，主要考虑你需要大量题库与答案管理功能。Django Admin 适合作为可信用户使用的内部内容管理界面，但不应该替代完整的学习前端；Django Ninja 则提供类型化 API、数据校验和 OpenAPI 支持。:chatgpt-content-reference{index="3"}

## 7.2 整体结构

```text
                    浏览器 / 手机浏览器
                             │
                     React Web 应用
                             │
                    Django Ninja API
                             │
       ┌─────────────────────┼──────────────────────┐
       │                     │                      │
   题库与内容模块       学习与考试模块          AI 服务模块
       │                     │                      │
   导入、版本、来源     判分、任务、复习       检索、讲解、校验
       │                     │                      │
       └─────────────────────┼──────────────────────┘
                             │
              PostgreSQL + pgvector + 文件存储
                             │
                      Celery / Redis
                             │
           文档处理 Worker / 模型调用 Worker
```

**不要一开始拆成很多微服务，也不用同时引入 FastAPI 和 Django。**

你的 Ubuntu＋4090 环境可以作为可选的本地推理节点，但 Web 服务本身不依赖 GPU。视觉、嵌入和讲解模型是否同时本地运行，应在候选模型确定后分别测试显存与延迟，不预设一张卡能同时承载所有模型。

# 八、数据库怎么设计

最关键的原则是：

**题目内容、考试中的题目记录、用户作答记录，必须分开。**

否则去重、版本修正、历年统计和学习状态都会混在一起。

## 8.1 核心数据实体

| 模块 | 主要表 | 职责 |
|---|---|---|
| 考试配置 | `exam_project`、`exam_spec`、`syllabus_version` | 目标、题型、评分规则、大纲 |
| 原始材料 | `source_document`、`source_region`、`import_job` | 文件、页码、图像区域、处理状态 |
| 题目内容 | `question`、`question_version`、`question_family` | 稳定题目身份、内容版本、同模板关系 |
| 试卷记录 | `paper`、`paper_item` | 哪年哪场考试出现哪道题、多少分 |
| 答案 | `answer_key_version`、`scoring_rubric` | 答案来源、验证状态、评分标准 |
| 考点 | `knowledge_node`、`prerequisite_edge`、`question_knowledge` | 考点与前置关系、分值归属 |
| 学习过程 | `practice_session`、`attempt`、`attempt_step`、`hint_event` | 原始作答、步骤、用时、提示暴露 |
| 辅导 | `tutor_session`、`tutor_turn`、`error_diagnosis` | 讲解内容、诊断证据、确认状态 |
| 学习状态 | `learner_knowledge_state`、`study_task` | 各考点证据汇总、今日任务 |
| 复习 | `review_card`、`review_log` | 记忆卡及调度记录 |
| 审计 | `llm_run`、`grade_event`、`content_revision` | 模型版本、评分变化、内容修订 |

这些是逻辑实体，首版可以合并少量实现表，但不要丢掉职责边界。

## 8.2 作答记录必须保留历史

`attempt` 至少要绑定：

```text
用户与学习会话
题目版本
当时的答案与评分规则版本
原始作答
作答步骤
耗时
提示与答案是否已展示
当时的评分结果
是否属于有效独立测验
```

后续发现标准答案有误时，新增评分修订事件，再重算受影响的学习状态；不要直接覆盖原始作答。

同样，修改题干或考点标签时，也需要知道哪些报告、解析缓存和学习状态需要更新。

# 九、LLM 应该负责什么，不应该负责什么

## 9.1 职责边界

| 工作 | 处理方式 |
|---|---|
| 理解截图、拆分题目 | 视觉模型提出结果，结构校验与必要校对 |
| 识别考点、方法、前置知识 | LLM 输出候选标签，受控词表约束 |
| 五年统计、分值汇总 | SQL / Python 计算 |
| 单选、多选判分 | 按考试规则确定性计算 |
| 数值、公式类答案 | 规则和受限校验工具优先 |
| 简答、论述评分 | 根据评分标准由 LLM 辅助，标记为估计评分 |
| 错误原因分析 | LLM 基于步骤提出诊断，证据不足时追问 |
| 个性化讲解 | LLM 结合题目、可靠答案和知识材料生成 |
| 下一题选择、复习时间 | 学习规则与调度器 |
| 变式题生成 | LLM 生成候选，校验后才发布 |

**不建议首版训练或微调自己的大模型。**先验证题库质量、判分准确性和学习闭环；这些部分没有做好，换更大的模型也不能替代它们。

## 9.2 检索不能只靠向量相似度

建议检索顺序：

```text
题目 ID 对应的完整题目
        ↓
绑定的答案和评分标准
        ↓
直接关联的考点材料、前置知识
        ↓
必要时进行关键词 + 向量混合检索
        ↓
返回带来源定位的信息
```

所有检索先限制：

```text
用户权限
考试项目
大纲版本
内容审核状态
是否属于封存测验题
```

pgvector 可以把向量放在 PostgreSQL 中管理，其官方文档也给出了与全文检索结合的混合搜索思路。对这个项目，先把权限、来源和题目关联做好，比单独增加一个向量数据库更重要。:chatgpt-content-reference{index="4"}

中文关键词检索需要明确的分词或索引方案，不能默认配置好 PostgreSQL 就已经具备理想的中文检索效果。

## 9.3 不需要自由行动的多 Agent 系统

建议使用固定流程：

```text
加载学习上下文
      ↓
判分或读取判分结果
      ↓
检索可靠依据
      ↓
诊断当前问题
      ↓
决定提示 / 追问 / 讲解
      ↓
生成结构化结果
      ↓
校验来源与输出
      ↓
展示结果
```

模型只提出教学内容和下一步建议，**不能直接修改数据库中的掌握状态、评分规则或任务队列**。

需要持久化和分支控制时，可以使用 LangGraph；但把它当工作流引擎即可。其官方文档也明确区分了预设路径的工作流与动态决定行动过程的 Agent。:chatgpt-content-reference{index="5"}

每个调用记录输入版本、模型、提示词版本、检索来源、延迟与费用；失败重试要有次数上限。

# 十一、必须提前处理的质量与安全问题

## 答案和生成题的质量

AI 生成的变式题单独标记，不与真题混淆；不得进入“五年真题频次”统计。

发布前至少检查：条件是否完整、答案是否能得到、单选是否只有一个正确项、是否偏离大纲。数值和符号计算尽量用受限工具校验；不能独立验证的题，需要人工核对。

两个模型答案一致只能作为辅助信号，不能代替标准答案或有效校验。

## 学习效果不能被“见过题”污染

预留一部分未向用户展示的题用于测验，并按题目家族隔离近重复题。封存题不能进入日常讲解检索、变式生成或练习推荐。

用于真实测验的题一旦展示过答案，就不再算“未见题”。

报告应区分：

```text
原题熟练度
陌生变式表现
延迟后的表现
限时测验得分
```

不能只根据日常正确率给出“通过概率 95%”。

## 权限与输入安全

上传内容和检索材料都当作不可信数据，不执行其中的指令。模型不应获得任意数据库写入、文件访问或代码执行能力。

原始文件私有保存、访问鉴权；上传限制类型和大小；题干和解析渲染时过滤危险内容；云端模型调用前支持去除姓名、学号等信息。

题库同时保存来源与使用范围，不把用户上传的材料默认公开给其他用户。

## 成本控制

客观题判分不调用 LLM；同一版本题目的基础解析缓存复用；只有个性化诊断部分实时生成。

离线批量标注与在线讲解使用不同任务队列，避免一次大批量导入阻塞正在刷题的用户。

缓存键至少包含：

```text
题目版本 + 答案版本 + 大纲版本 + 提示词版本 + 模型版本
```

# 十二、实际开发顺序

建议按“先可靠、再个性化、最后复杂化”的顺序推进。

| 阶段 | 交付内容 | 验收重点 |
|---|---|---|
| **第一阶段：可靠题库与讲题** | 一个考试项目；图片/文字导入；校对；答案来源；客观题练习；按需讲解；作答记录 | 导入后能正确作答、判分、追溯来源，识别问题不会悄悄进入题库 |
| **第二阶段：考点与补弱闭环** | 考点标签；五年统计；错误诊断；学习状态；今日任务；间隔复习 | 每项推荐都有依据，提示后答对不会被当成独立掌握 |
| **第三阶段：迁移与考试验证** | 校验后的变式题；主观题评分适配；封存测验；限时模拟；学习效果报告 | 陌生题、延迟题和限时测验是否真正改善 |

开发开始时就准备一个人工核对的小型测试集，覆盖普通文字题、公式、表格、跨页题、模糊图片、答案冲突和多选计分。每次更换模型或提示词，都回归测试，不只凭聊天体验判断效果。

**第一版最重要的验收标准，是同一个学习闭环能够完整跑通：**

> 上传一道题 → 正确入库 → 记录你的作答 → 找到具体卡点 → 讲清楚 → 用另一道题验证 → 在之后的复习中再次验证。

先把这个闭环做扎实，再批量导入五年真题，系统才会从“AI 题库”变成真正帮助你选择学习重点、减少重复错误、验证提分效果的工具。
